# MCP Migration Plan — fluvioMe Tools

> **Goal:** Replace the bespoke, double-JSON-encoded `executeTool` contract with the
> **Model Context Protocol (MCP)**. Expose `fluvio-tool-builder` as an MCP server that
> the `agent-planner` consumes internally **and** that any external MCP client
> (Claude Desktop, Cursor, the Claude API MCP connector) can connect to.
>
> **Status:** Plan — no code yet. Decision locked: **internal + external** exposure.

---

## 1. Why MCP

### The ugliness today (verified in code)
The worker calls tools through a string-typed escape hatch:

```python
# agent-planner/app/jobs/worker.py
inputs_str = json.dumps({"action": action, "arguments": json.dumps(arguments)})
executeTool(toolId: tool_id, inputs: inputs_str)   # GraphQL: inputs: String!
```

That's **JSON inside JSON inside a GraphQL string**. And the tool's real input schema
is not machine-readable at all — in `dashboard_syncer/manifest.json` the `arguments`
parameter is literally described as:

> `"JSON string of parameters defined in contracts.py..."`

So today an LLM has to read prose to guess the argument shape, and the planner
hand-injects a custom `toolbox.format_for_prompt()` blob into Claude's system prompt.

### What MCP gives us
| Concern | Today | With MCP |
|---|---|---|
| Tool call contract | `executeTool(id, "json-in-json")` | typed `tools/call {name, arguments}` |
| Input schema | prose in `manifest.json` | real **JSON Schema** per tool (`inputSchema`) |
| Discovery | scan a manifests dir | standard `tools/list` (introspectable) |
| Feeding the LLM | custom prompt injection | native tool schemas (Claude/any LLM) |
| External reuse | ❌ nobody else can call our tools | ✅ any MCP client (Claude Desktop, Cursor, …) |

### The strategic win (why external matters)
fluvioMe is an open-source headless engine. If our pipeline + report-generation tools
speak MCP, **any agent ecosystem can drive them**. A user in Claude Desktop could say
"build a churn pipeline from my Postgres and email me the PDF" and our tools execute it.
That is free distribution and the strongest reason to do the external server, not just
the internal swap.

---

## 2. What MUST NOT change (the moat)

MCP replaces **tool transport + discovery only**. It does **not** replace orchestration.
These stay exactly as they are in `agent-planner`:

- plan → compile → deploy flow (`routers/chat.py`, `compile.py`, `execute.py`)
- async job queue + background worker (`jobs/worker.py`, `jobs/store.py`)
- reliability: retry, circuit breaker, idempotency, rollback (`reliability/`, `rollback.py`, `idempotency.py`)
- SSE log streaming, audit trail (`audit/`)

> Raw MCP has none of that. The orchestrator deciding *which* tools to run, in what
> order, with what reliability, **is fluvioMe's value-add**. MCP is just how the worker
> *calls one tool*. Keep that boundary crisp.

## 3. Current → Target architecture

### Today
```
agent-planner (worker)
  └─ GraphQL mutation executeTool(toolId, inputs: "json-in-json")
      └─ gateway :4001
          └─ fluvio-tool-builder :3008  (DynamicRegistry.execute_tool_action)
              └─ import src.tools.<tool>.runtime → <Tool>Runtime().<action>(**pydantic_args)
```

### Target
```
                          ┌────────────────────────────── external MCP clients
                          │   Claude Desktop · Cursor · Claude API MCP connector
                          ▼
fluvio-tool-builder :3008  ── MCP server (Streamable HTTP transport) ──┐
  tools/list   → schema per (tool, action) from Pydantic contracts     │
  tools/call   → DynamicRegistry.execute_tool_action (unchanged core)  │
                          ▲                                            │
agent-planner ── MCP client ─────────────────────────────────────────┘
  compile.py : tools/list  → feed real schemas to Claude (delete prompt hack)
  worker.py  : tools/call   → replaces executeTool double-encode
```

`DynamicRegistry.execute_tool_action()` stays as the execution core — MCP just wraps it.

## 4. The schema mapping (this is the crux, and it's easy)

A fluvioMe "tool" today = `tool_id` + multiple **actions** (methods on the `*Runtime`
class), each taking **Pydantic-typed** arguments (`contracts.py`).

MCP tools are flat: `name` + `description` + `inputSchema` (JSON Schema). So map
**one MCP tool per (tool_id, action)**:

| fluvioMe | MCP tool |
|---|---|
| `dashboard-syncer` / `publish_report` | name: `dashboard_syncer__publish_report` |
| `dashboard-syncer` / `generate_pdf_report` | name: `dashboard_syncer__generate_pdf_report` |
| `spark` / `execute_sql` | name: `spark__execute_sql` |

`inputSchema` comes free from Pydantic:
```python
# the args model for an action already exists in contracts.py
PublishReportArgs.model_json_schema()   # → valid JSON Schema, descriptions included
```

So the MCP tool list is generated by:
1. `DynamicRegistry.get_all_tools()` → tool ids
2. For each runtime class, `inspect.signature` each public action method (already done in `execute_tool_action`)
3. For each action's Pydantic arg model → `model_json_schema()` → `inputSchema`
4. Description = action docstring + manifest description

**No manual schema writing.** The prose `arguments` field in `manifest.json` is deleted
in favor of generated schemas.

---

## 5. Transport decision

Use **Streamable HTTP** (MCP's HTTP+SSE transport), not stdio:
- Works across the docker network (planner → tool-builder) and remotely.
- One endpoint, e.g. `POST :3008/mcp`, alongside the existing GraphQL — no new port.
- External clients connect to the same URL (behind the gateway / their own auth).
- stdio transport is for local single-process clients only — wrong fit here.

Python: use the official `mcp` SDK (`pip install mcp`) which ships a Streamable HTTP
server. It coexists with the FastAPI app already running on `:3008`.

## 6. Migration phases (incremental, non-breaking)

### Phase M1 — Stand up the MCP server (additive, nothing removed) ✅ DONE & VERIFIED
- ✅ Added `mcp>=1.2.0` to `fluvio-tool-builder/requirements.txt` (installed: mcp 1.27.2)
- ✅ `src/mcp_server/schema.py` — discovers **25 tool-actions** across 9 tools; generates
  `inputSchema` from method signatures (Pydantic `context` → nested object schema, scalars typed)
- ✅ `src/mcp_server/server.py` — low-level `Server` + `StreamableHTTPSessionManager`;
  `list_tools`/`call_tool` delegate to the unchanged `registry.execute_tool_action`
- ✅ Mounted at `/mcp` in `src/main.py`; `mcp_lifespan` nested in the service lifespan
- ✅ `executeTool` GraphQL untouched — verified both paths respond on the same process
- ✅ **Verified live:** MCP client `tools/list` → 25 tools; `tools/call database__list_tables`
  → executed against the real DB and returned actual table names. GraphQL `availableTools`
  still works simultaneously.
- Naming convention chosen: `<snake_tool_id>__<action>` (e.g. `dashboard_syncer__publish_report`).

### Phase M2 — agent-planner becomes an MCP client (compile path) ✅ DONE & VERIFIED
- ✅ `app/capabilities/mcp_client.py`: `list_tools()` (full specs), `list_tool_names()`,
  `format_tools_for_prompt()`, `call_tool()`. `mcp_server_url` config (default :3008/mcp).
- ✅ `routers/compile.py`: injects the **live MCP tool schemas** (name + args + required,
  derived from each tool's `inputSchema`) into the system prompt, best-effort.
- ✅ `toolbox.validate_steps()` kept as the fallback validator (non-breaking).
- ✅ Verified live: the prompt section renders real schemas (`airflow__get_dag_run_status`
  → `args: context, dag_id, run_id · required: …`).

### Phase M3 — agent-planner worker calls tools via MCP (deploy path) ✅ DONE & VERIFIED
- ✅ `jobs/worker.py`: `_call_tool` now prefers typed MCP `tools/call`
  (`tool_id__action`), falling back to the legacy `executeTool` mutation **only** when the
  MCP server is unreachable. A tool that runs and fails does NOT fall back (no double-run).
- ✅ **Reliability wrapper unchanged** — `with_retry`, circuit breaker, idempotency still
  wrap `_call_tool`. Only the innermost invoke line changed.
- ✅ Verified live: `_call_tool(None, "database", "list_tables", …)` — `client=None` proves
  the legacy path is impossible — returned `status: success` with real DB tables via MCP.

### Phase M4 — External exposure
- Expose the `/mcp` endpoint through the gateway (or a documented direct URL).
- Auth: require `x-fluviome-token` for external callers (ties into the enterprise gate);
  community/self-host can run open. Decide per deployment.
- Publish a Claude Desktop / Cursor config snippet in `/docs`:
  ```json
  { "mcpServers": { "fluviome": { "url": "https://your-host/mcp" } } }
  ```
- ✅ Done when: Claude Desktop lists fluvioMe tools and can run one end-to-end.

### Phase M5 — Retire the old path (optional, later)
- Once M2+M3 are stable, deprecate `executeTool(inputs: String!)`.
- Delete the prose `arguments` blobs from `manifest.json` (schemas now generated).
- Keep `manifest.json` for id/name/category/description only.

## 8. Open questions to resolve during M1

1. **Tool naming:** `dashboard_syncer__publish_report` (double underscore) vs nested — MCP
   names must be unique flat strings; pick a separator and stick to it.
2. **Credentials:** today the worker injects `database_url`/tableau/powerbi into
   `arguments.context` at execution time. Decide whether that injection stays in the
   worker (yes, for internal calls) and how external MCP callers supply credentials.
3. **Auth for external `/mcp`:** `x-fluviome-token` gate vs open self-host — likely a
   config flag mirroring the enterprise model.
4. **Streaming:** MCP supports progress/partial results; map our SSE log lines onto MCP
   progress notifications, or keep logs on the existing `/jobs/{id}/stream`.

---

## 9. Why this ordering is safe

Each phase is **additive until M5**. The old `executeTool` path keeps working through
M1–M4, so we can ship and test the MCP server, then the compile path, then the deploy
path independently — and roll back any single phase without breaking deploys. The
orchestration/reliability layer is never touched, only the innermost transport line.
